# Architecture

## Package boundaries

`contracts` owns Zod schemas and inferred TypeScript types. `core` owns pure language, intent, importance, reply, privacy and escalation rules. `knowledge` owns provider interfaces, normalization, mapping, retrieval and cache contracts. `ui` owns shared components. `test-fixtures` owns synthetic DOM and fictional business datasets.

The extension contains a thin DOM adapter and a restartable service worker. The worker coordinates profiles, settings, knowledge, backend requests, persisted drafts, takeover, tickets, notifications and alarms. The backend keeps keys and owns grounded generation, persistent ticket repositories, notifications and audit metadata.

Allowed dependency direction: apps → core/knowledge/ui/contracts; core and knowledge → contracts; contracts → Zod only. Core never imports DOM, Chrome or transport code. UI and knowledge remain outside content scripts.

## Tooling choices

Node 24 is the installed LTS line, pinned to 24.22.1 ([Node download](https://nodejs.org/en/download)). pnpm 11.25.0 matches the installed workspace manager and is pinned in packageManager. Direct tool versions are exact and transitive resolutions belong in pnpm-lock.yaml.

The package store is local to `.pnpm-store/` and ignored by Git. This keeps installation writes within the workspace and lets ordinary frozen installs reuse the same store. The 24-hour dependency age gate and no-downgrade trust policy remain enabled; initial metadata downloads can take longer on a slow connection.

TypeScript project references emit independent ESM modules and declarations. NodeNext resolves `.js` imports consistently in emitted Node code. Browser React/Vite packages can extend the base with bundler resolution and DOM libraries when introduced. Strict mode, unchecked-index checks, exact optional properties, unused-code checks, and explicit package exports make boundaries visible.

ESLint uses flat configuration and the compatible typescript-eslint preset. Prettier owns formatting independently. Vitest runs contracts in Node without Chrome or a real WhatsApp account. Test and tool configurations are typechecked separately from emitted production source.

Resolved toolchain: TypeScript 6.0.3, ESLint 10.13.0, @eslint/js 10.0.1, typescript-eslint 8.72.0, Prettier 3.9.10, Vitest 5.0.5, Zod 4.6.7, and Node declarations 24.19.2. TypeScript 7.0.2 is newer, but typescript-eslint's published peer range requires TypeScript below 6.1.0. Pin the compatible 6.0.3 release until the linter supports the next compiler. Node declaration types stay on the runtime's major version.

Milestone 1 uses React 19.3.1 and Vite 8.3.5 with their built-in TypeScript/JSX support. Vite produces three HTML pages and a deterministic service-worker.js entry, shared local chunks and a manifest generated from manifest.config.ts. The worker is an ES module. Strict CSP permits only bundled scripts/styles and same-origin connections. Fastify/SQLite remain deferred to the backend milestone.

Browser TypeScript extends the strict base with Bundler resolution, DOM/Chrome types and React JSX. Declarations go to .types; Vite owns the production dist directory. React Testing Library and jsdom exercise UI behavior; Playwright loads the actual unpacked extension in isolated bundled Chromium. CI installs that browser and runs all checks.

pnpm 11 workspace settings, including storeDir, saveExact, engineStrict and strictPeerDependencies, live in pnpm-workspace.yaml. Earlier .npmrc-only store configuration was not applied consistently to filtered dependency installs; the workspace setting now enforces the project-local store.

## Historical Milestone 1 shell implementation

Only storage and sidePanel permissions are requested. Storage persists profile/settings; sidePanel opens the reply workspace from an explicit popup click. There are no host permissions, content scripts, tabs, identity, alarm or notification permissions in Milestone 1. The popup reports adapter pending rather than inferring a WhatsApp connection.

Shell messages are strict versioned requests with validated responses. The router accepts only its own popup.html, sidepanel.html and options.html top-level extension pages, verified by extension ID, protocol, host, path and frame. Content scripts and arbitrary extension documents cannot mutate settings through these routes. Send/insert events are unsupported in this milestone.

All local settings writes pass through one worker repository, with a serialized mutation queue and monotonically increasing revision. Options edits carry the revision they started from. A stale edit fails without overwriting newer settings; the dirty form remains visible for review. Invalid stored data is not silently reset. UI pages subscribe to local/session changes and retrieve validated state from the worker.

The fixed bakery demo emits ASSISTANT_DECISION_READY with a synthetic profile-scoped hash, citations and DRAFT policy. Only fictional data is stored in chrome.storage.session. GET_STATE filters session samples to the active profile, so another business's sample is not displayed. Editing a draft is page-local. Recreating the worker restores persisted settings and the session sample. Browser restart clears the session sample.

## Contracts and trust

Version 1 extension events are strict discriminated unions with bounded strings. Chat-scoped events include profile IDs and SHA-256-shaped keys. Incoming messages are restricted to incoming direction. Answer decisions require citations and a DRAFT policy. Send requests carry an explicit-click marker; a future trusted UI handler must verify the actual interaction, sender, active chat and draft before performing a send.

Server requests reference server-owned profiles; they cannot replace policy with client-provided profiles. Shape validation does not prove tenant ownership, citation relevance, notification delivery or endpoint safety. Enforce these at the corresponding runtime boundary.

## Persistence and transports

Use chrome.storage.local for small settings and profile metadata, IndexedDB for knowledge, tickets and minimal event history, and chrome.alarms for persisted delayed follow-ups. Namespace every key by profile. Store pending state before scheduling and reconcile on restart.

The future transport interface covers incoming structured events, approved draft insertion, send capability and delivery results. Web transport requires explicit human approval. Official transport can apply automatic-send policy. Both reuse the same core, knowledge, ticket and audit contracts.

## Architecture work deferred after Milestone 1

The local pairing and provider boundary is implemented below. Hosted authentication, durable customer-data migrations/retention, remote knowledge destinations, tickets and alarm state-machine invariants remain deferred.

## Implemented local adapter/backend boundary (2026-10-28)

This section supersedes the Milestone 1-only descriptions above for the current integrated release. Native Node HTTP and fetch provide a small typed loopback service without adding framework/SDK dependencies. No database is needed because this slice does not persist customer messages or workflow records. The exact pinned toolchain remains unchanged.

The production manifest adds only `https://web.whatsapp.com/*` and `http://127.0.0.1:3000/*` host grants. It retains storage/sidePanel permissions. A separate Vite build emits a standalone IIFE content script: it cannot import worker/UI chunks. CSP permits packaged code and the fixed loopback connection. A separate fixture manifest grants ports 4174/4175 for tests; production artifact checks reject these origins.

The content adapter centralizes ordered, validated CSS selector packs. It baselines existing nodes without extracting history, waits for hydration, ignores outgoing and prepended history, and deduplicates public DOM message IDs/events. Chat keys hash per-install salt, business ID and public DOM identity. Conservative list replacements reset context. Titles alone can support suggestions but cannot authorize insertion. New-node hydration may be deliberately ignored while baselining, so this is not a reliable-delivery transport.

Content-script events carry validated profile/chat/context identities. Worker routing verifies own extension ID, WhatsApp URL, tab and top frame separately from trusted extension-page routes. UI settings cannot be changed through content routes. Insertion revalidates active target tab, current profile/chat/context, stable DOM identity and empty composer. It inserts text only. There is no send-button execution.

The worker keeps live text/replies in memory. Settings, salt, profile-scoped pairing capabilities and bounded hashed event/cooldown timestamps persist in trusted-context local storage. Restart loses suggestions and rebaselines tabs, preventing history replay. Same-context status refreshes preserve pending generation identity; chat/profile changes invalidate it.

The backend binds 127.0.0.1 only. Setup uses an HttpOnly SameSiteStrict session cookie and a session CSRF token for writes; Host and Origin checks reject foreign browser origins. API requests require a random profile-scoped pairing capability checked with constant-time comparison. Profiles sync only through that authenticated path, and assist requests reference the server-owned profile. Customer text cannot supply a replacement system policy. Revocation removes the key and invalidates pairing.

API keys entered through setup are moved into backend process environment variables; configuration objects hold environment-variable names only. No key is returned to the extension or echoed by setup. Input fields clear after submission. Runtime keys and configuration disappear when the server exits. Optional ignored .env startup configuration is for this operator's local environment, not a shared key vault. The setup page is disabled until its initial state loads, avoiding late-response overwrites.

Provider destinations are fixed in code; no custom endpoint field exists. Redirects are rejected, requests time out, JSON is bounded/validated and failures expose only bounded error codes. OpenAI uses Responses with JSON schema and store:false; Gemini uses generateContent JSON mode with post-validation; Anthropic uses Messages JSON schema with its documented API version. Models must support the selected API/output mode. Reference: [OpenAI structured output](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses), [Gemini generateContent](https://ai.google.dev/api/generate-content), [Anthropic Messages](https://platform.claude.com/docs/en/api/messages/create).

Pure core code constructs system rules plus operator instructions and separates customer/knowledge data in the model input. It checks response shape, evidence, exact numeric tokens, money and URLs against the operator-entered knowledge record; unsupported output becomes a localized handoff draft. Greetings can be nonfactual without evidence. English action-claim guards and lexical checks are not a multilingual semantic verifier. No ticket/notification action exists and no success may be inferred. The backend also blocks configured-key text in profile fields and redacts key echoes in replies. Human review remains mandatory.

Structured working hours, enable/mode, auto-suggestion consent, cooldown and bounded reply delay are enforced. Delays above five seconds are rejected rather than promised across worker termination; durable scheduling belongs to the future alarms milestone. Operator instructions are flexible language instructions, not executable configuration or a replacement for these enforced gates.

## Explicitly authorized web Auto-reply — extension 0.3.0

The operator's 2026-11-01 instruction “Send automatically—change the project rule” supersedes the manual-only web restrictions above for the new `AUTO_REPLY_WEB` mode. DRAFT_ONLY remains the default; the official transport mode remains unavailable. A separate saved boolean consent is required by profile/edit validation, preserved across unrelated edits and cleared when switching off or back to drafts. Auto mode authorizes generation even if the earlier automatic-suggestion checkbox is off. No Chrome permissions or remote executable code are added.

The worker owns eligibility, per-chat pause, cooldown and delivery state. Only a fresh ADAPTER_MESSAGE may initiate automatic delivery; manual generation never sends. Human-help output, stale generation, changed settings/profile/chat, a paused chat, configured closed hours or an inactive tab prevents sending. A configured outside-hours DRAFT action can generate a draft but never authorizes automatic sending outside the actual schedule. Freshness uses the configured duplicate window capped at 300 seconds, independently checked by the worker and adapter. Default pauses are empty; pauses are keyed by the business-scoped hashed chat key, persist until explicit release and block new automatic generation/actions. With title-only identity, identical chat titles conservatively share a pause/cooldown hash; source-node binding still prevents cross-chat insertion.

Before issuing a send command, DeliveryJournal serializes and persists an ATTEMPTING reservation keyed by a hash of profile/chat/event. Each stored entry's key is checked against its owner fields. No raw question, generated reply, label, public message ID or provider key is stored. Entries expire after the profile's configured retention, cleaned on the next journal operation; a maximum of 512 unexpired entries fails closed rather than evicting a possibly sent attempt. Storage errors/corruption prevent automatic sending. Final states are SENT, BLOCKED or UNCERTAIN; any existing reservation blocks reattempt after worker restart. An interrupted operation remains ATTEMPTING. This bounded local-development journal is not a production delivery database.

The content adapter retains only the latest newly observed incoming source in memory: exact DOM node, public ID, observed text and observation time. It verifies source continuity and unchanged text, current context/list/header, no subsequent message row, visible document and an empty composer before insertion. This also permits explicit insertion on the newly observed opaque-ID layout without pretending its title is a strong identity. After insertion it waits up to 1.5 seconds for a scoped enabled native footer button, verifies exact composer text and requests a final authorization from the worker. The worker matches its pending delivery ID, sender tab/frame, profile/chat/context, source event, reply hash, settings revision, pause and active tab. Missing pending state after worker restart denies authorization. No asynchronous operation separates the adapter's final DOM checks from the native click. A click is never retried automatically; a cleared same-context composer within 1.5 seconds yields SENT, which means acceptance by the host UI, not delivery over the network. Failed checks may leave the generated draft for manual review; existing operator text is never overwritten or cleared.

The extension now depends on the existing pure core workspace package to reuse the working-hours policy; no external versions change and the workspace link is recorded in pnpm-lock.yaml. The backend continues generating drafts only: BackendClient omits client-only consent and projects AUTO_REPLY_WEB to DRAFT_ONLY when syncing. This keeps the already-running local backend and its transient key/pairing compatible, without adding a backend sending endpoint. Prompt/grounding limitations described above still apply; opt-in automatic delivery removes the human review gate for eligible output.

## Cooldown continuation — extension 0.3.1

A deterministic regression reproduced the screenshot: a second incoming event replaced an in-flight suggestion with ERROR/COOLDOWN, invalidating the first response without starting a new request. The worker now maintains at most one automatic generation per profile/chat and a replaceable pending item per tracked tab. New text invalidates older generation output and replaces the pending item. Generation starts after both the in-memory generation interval and the persisted delivery-journal cooldown expire. All existing source, profile/revision, readiness, takeover, composer, active-tab and delivery-claim gates still apply. A cooldown rejection never clears the claim journal or authorizes a resend. Settings expose the existing perChatCooldownSeconds field; absent fields in older edit requests preserve its value, including zero.

The content bridge advances pending work using strict ADAPTER_POLL context-only messages at the worker's requested interval (currently one second). The bridge never rereads message history or decides cooldown policy. Only a validated acknowledgement to a new incoming event starts polling. No more polling is requested after work starts or is canceled; epoch checks cancel stale callbacks on a newer event, context change, reset or disposal. Polling independently stops after five minutes; the worker's source freshness limit (configured duplicate window capped at 300 seconds) can cancel it earlier. Intervals exceeding freshness produce COOLDOWN_TOO_LONG; elapsed sources produce MESSAGE_EXPIRED, both with actionable UI text.

This avoids depending on a worker setTimeout surviving suspension: [Chrome's lifecycle documentation](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle) describes idle termination and extension events resetting its timer. Rechecks are bounded live work, not an indefinite keepalive or a durable follow-up scheduler. Unexpected restart discards volatile queued text, rejects old polls and rebaselines DOM history. Persisted hashed seen/delivery metadata prevents replay and preserves send cooldown for fresh post-restart events. Pause/resume, profile/settings changes, chat switch, tab closure/eviction and reconnect cancel pending work. No new external dependencies, Chrome permissions or backend API changes are needed; pinned Node/pnpm versions remain unchanged.

ComposerInsertion owns only a write into an initially empty editable in the current #main footer. It reacquires the configured editable within that same connected footer, compares bounded DOM display text (paragraphs/BR, emoji alt text, NBSP-to-space and CRLF-to-LF), and preserves all other internal whitespace, punctuation and identifiers. Unsupported image representations or deep/oversized trees fail closed. Trusted input, keyboard, paste/drop or pointer activity in that footer after the synchronous insertion cancels ownership, including edit-and-undo. Synchronous events raised by the adapter's own editing operation are distinguished from later user editing. Equivalent remounts may settle during the existing 1.5-second button wait; replacement of the entire footer is not followed. Final source/context/worker authorization, empty-before-write, exact display text and button checks still precede the sole native click. Composer acknowledgement may follow an equivalent remount as well. Ownership is volatile and ends with the attempt; pre-existing or post-reload text is never adopted merely because it matches an AI reply.

For automatic generation only, needsHuman output is replaced in the worker by safeFallback(detectLanguage(newText, profile)); provider fallback wording is not trusted. The live state retains needsHuman plus a standardFallback marker for truthful display. Authorization requires the exact worker-defined localized fallback as well as all normal identity, consent, pause, hours, active-tab and durable claim gates; the marker alone cannot authorize a send. Draft only and explicit manual generation retain review. This supersedes the earlier blanket needsHuman block for the fixed automatic fallback only. It does not create tickets, notify a team or promise callbacks. No API keys, backend endpoints, permissions, external dependencies, storage format migrations or source-history reads are added.

## Repeated replies after worker wakeup — 0.3.3

Startup previously ran the same ADAPTER_RESET path as explicit reconnect. When a new event woke a suspended worker, that reset could rebaseline the already-observing content adapter and swallow the waking message. Startup now uses a strict versioned ADAPTER_RESUME control. If bootstrap configuration is unchanged, the adapter serializes a metadata-only scan/reannouncement with its observer chain, retaining context, seen IDs and deduplication. Changed configuration and explicit reset still configure/rebaseline. A healthy resume does not cancel a newly established pending-poll lease. Missing/older receivers still recover through packaged top-frame isolated injection. These controls retain the trusted-worker sender check; content requests retain origin/tab/frame verification.

Every newly observed message forces an acknowledged status registration before its raw text event, even if diagnostic metadata has not changed. Generation/context/DOM identity are checked again after that asynchronous acknowledgement. A newly started worker can accept the fresh event without restoring raw messages from storage. Raw in-flight/queued state is still volatile; previously seen events and attempted deliveries are not replayed.

A separate regression showed a sent row being replaced with an equivalent DOM node in the same batch as the next incoming row. Previously the missing tail object rebaselined both. The adapter now records its observed public tail ID: exactly one matching row in the same unchanged message container may replace the tail anchor. Nodes up to that anchor are baselined without reading text; only new append mutations after it remain eligible. Missing/ambiguous IDs, changed container/chat/configuration and startup still use conservative baselines. Source-bound send checks continue to require the latest incoming node/text/ID and all worker authorization gates.

Chrome's documented [worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle) permits idle termination; this repair supports restart instead of keeping the worker alive indefinitely. The fixture browser uses the [ServiceWorker.stopWorker protocol command](https://chromedevtools.github.io/devtools-protocol/tot/ServiceWorker/#method-stopWorker) to stop the actual extension worker twice between same-chat replies, then observes fresh incoming events and automatic sends without reloading the page. The fixture also remounts the outgoing tail before new input. No dependencies, permissions, API configuration, pairing or raw-data persistence change.

## Restart-stable backend environment configuration — 0.3.4

This section supersedes the earlier session-only setup description for operator-selected remembered connections. The screenshot's UNAUTHORIZED follows a backend restart: the prior process held the only configuration/key and randomly generated pairing. Re-entering the provider key alone creates a different token, leaving the extension's previously stored capability invalid. Remember connection on this PC now saves both credentials and the same capability. It is initially selected when persistence is available; session-only remains an explicit choice. Expired credentials from previous versions cannot be recovered; one final configure/pair step is required after upgrading.

The production server fixes the path to the repository-root Git-ignored `.env.connections`, independent of working directory. The environment file contains one versioned variable with a base64url-escaped strict JSON array, capped at 32 unique profiles/tokens and 64 KiB. Encoding is not encryption. Only profile ID/provider/model/API key/pairing are saved, never raw chats, instructions, profiles, pending generation, delivery claims or model replies. Validated keys are imported into private per-process environment variables; configuration objects retain environment-variable names. Test/embedded instances remain volatile unless explicitly passed a connection-file path. No HTTP request can select a filesystem path.

Writes validate before mutation, create an exclusive random same-directory temporary file, restrict permissions before writing secrets, flush the file and atomically rename it. Unix creation uses 0600; Windows grants only current-user and SYSTEM access using fixed packaged OS executables, no shell evaluation. See [Microsoft icacls documentation](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/icacls). No directory ACL is changed. The environment loader uses Node's built-in [parseEnv](https://nodejs.org/download/release/latest-v24.x/docs/api/util.html#utilparseenvcontent), available in the pinned Node line; no dependency is added. Missing files mean first use; oversized, nonregular/symlink, invalid-schema or duplicate-owner/token files stop startup with a generic message. Failed saves leave active settings unchanged and return CONFIGURATION_SAVE_FAILED without secrets. This remains a trusted local-development environment file, not an encrypted vault or hosted tenant credential service. Protect it from sharing/backups.

Configuration changes preserve the pairing token for the same business. Unchecking Remember removes that entry from disk but retains it for the active session; explicit Remove persists deletion before revoking the live token. Backend close clears live environment keys without deleting remembered entries. Once a saved-connection file exists, it is authoritative over first-use LLM_* environment seeding, including an intentionally empty file after revocation. This prevents a removed connection being resurrected from an older `.env` seed. Other profiles remain isolated. Business policy is resynced through the existing authenticated endpoint before each generation after restart.

UI notices distinguish rejected pairing from rejected provider credentials and open only the fixed loopback setup origin with the encoded active profile ID. No automatic pairing recovery, key export, blanket authorization, replay of missed messages or send-policy change is introduced. Saved connections survive process/computer restarts; external key revocation, file deletion, port conflicts and WhatsApp DOM changes can still require operator action.
